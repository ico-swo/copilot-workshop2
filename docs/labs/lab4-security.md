# Lab 4 — Security with CodeQL and Copilot Autofix

**20 minutes.** Outcome: every code scanning alert has a recorded decision — fixed with a
regression test, or dismissed with a written reason.

## 1. Enable code scanning

1. **Settings → Advanced Security** (under *Security and quality* in the sidebar).
2. Next to **CodeQL analysis**, choose **Set up → Default**.
3. Confirm JavaScript/TypeScript is selected, then **Enable CodeQL**.

The first analysis takes a few minutes. Read section 2 while it runs.

## 2. What to expect

Open **Security → Code scanning**. Expect **five open alerts**. The goal is not to make them
all disappear — it is to make the right decision about each one.

| Alert | File | Decision |
|---|---|---|
| Reflected cross-site scripting (×2) | `src/legacy/label-printer.ts` | **Fix** |
| Clear-text logging of sensitive information | `src/db/seed.ts` | Triage: fix or dismiss |
| Clear text storage of sensitive information | `public/api-client.js` | Triage: fix or dismiss |
| Use of password hash with insufficient computational effort | `src/modules/auth/repository.ts` | Triage: fix or dismiss |

## 3. Read an alert properly

Open one of the XSS alerts and read, in order:

- the **rule** and what class of weakness it describes,
- the **data flow** CodeQL traced — from `req.url` to the HTML response,
- the **affected line** in `src/legacy/label-printer.ts`.

Then ask Copilot to ground it in this codebase:

```text
Explain the reflected XSS alerts in #file:src/legacy/label-printer.ts. Which request
values reach the response, what could an attacker do against a warehouse label
terminal, and which rule in .github/copilot-instructions.md does this break? Why are
there two alerts?
```

There are two alerts because there are two `res.end()` calls that each put request input
into HTML — one for an unknown SKU, one for a normal label. One cause, two sinks.

## 4. Reproduce it

An alert you have not seen fire is an alert you will not take seriously. With
`npm run dev` running:

```bash
curl -s "http://localhost:3000/legacy/label?sku=AOP-BRK-1001&operator=%3Cscript%3Ealert(1)%3C%2Fscript%3E"
```

The `<script>` tag comes back as live markup.

Now the contrast: in the dashboard, with the operator key, create a part named
`<script>alert(1)</script>`. It shows as plain text, because `public/app.js` only uses
`textContent`. Same input, different sink, different outcome.

## 5. Fix with Copilot Autofix

On each XSS alert, choose **Generate fix**. Before accepting, answer:

1. Does this actually remove the weakness, or only move it?
2. Does it change behaviour the label printers depend on?
3. Are the tests in `tests/legacy-label.test.ts` still meaningful?
4. Would I approve this from a colleague?

Autofix suggestions are generated by an AI model and are not guaranteed to be correct,
complete or secure. Review, validate and test before merging.

**Discuss in your pair:** Autofix will most likely escape the values, which closes the
alert. The repository standard says *never render a request value into an HTML string*.
Is escaping enough? Write your answer in the pull request description.

## 6. Add a regression test

```text
Add a test to #file:tests/legacy-label.test.ts proving that the operator and sku
parameters are never returned as live markup. Follow
#file:.github/instructions/tests.instructions.md, then run npm test.
```

## 7. Triage the other three alerts

These three were not planted — CodeQL found them on its own. The right answer depends on
context, so each one gets a decision, and the decision gets written down.

**Clear-text logging — `seed.ts`.** The seed script prints the three workshop API keys.

- *Fix:* print only the role names and point to the README for the keys.
- *Dismiss → "Used in tests":* these are disposable workshop keys.

**Clear text storage — `api-client.js`.** The dashboard keeps the API key in
`sessionStorage` so it survives a page refresh.

- *Fix:* keep the key in memory only, and re-enter it after a refresh.
- *Dismiss → "Won't fix":* state the trade-off, and that the app sets a strict
  Content-Security-Policy and never uses `innerHTML`.

**Password hash — `auth/repository.ts`.** CodeQL sees SHA-256 and assumes it is hashing a
password. It is hashing an **API key**. Slow hashes such as bcrypt exist for short,
human-chosen passwords; for long random keys, SHA-256 is standard practice.

- *Dismiss → "False positive":* write that this is an API key, not a password.
- *But note the real risk:* `aoph_operator_workshop_key` is easy to guess, and no hash
  would protect it. Production keys must be random — at least 32 bytes from
  `crypto.randomBytes`.

To dismiss: open the alert → **Dismiss alert** → choose a reason → write a comment. The
comment is the audit trail for the decision. A dismissal without a reason is not accepted.

## 8. Merge through the normal flow

Open one pull request with the XSS fix and the new test. Let CI run, get a review from your
partner, and merge. CodeQL re-runs and closes the fixed alerts automatically.

## Checkpoint

- [ ] CodeQL enabled and the first analysis completed
- [ ] Both XSS alerts reproduced, fixed with Autofix, and covered by a test
- [ ] The other three alerts each fixed or dismissed with a written reason
- [ ] Zero open alerts on `main` without a recorded decision

## Takeaway

CodeQL finds; Autofix proposes; people decide. Two alerts were real and got fixed. One was
technically wrong but pointed at a real risk. Two were trade-offs that needed a documented
choice.
